## 1. Project understanding ⚠ SUPERSEDED — see 11 Aug PO minutes

Healthcare robot domain. Robots administer and track medication for patients.

Domain model agreed in discussion:
- ~~**Users = robots.** Each robot is an authenticated client of the system.~~
  **CORRECTED (11 Aug):** there are **human users with role-based access** — healthcare professionals, caregivers, and admins. The client (phone / local machine) is one participant, not the only user.
- **Patients** are the subjects the data is about. Separate entity from users. — *still correct.*
- ~~Robots identify a patient (e.g. facial recognition), read their medication history, administer, and write the record back.~~
  **CORRECTED (11 Aug):** the client **reminds** the patient and records what they self-report; it does not administer anything. Identification is a mandatory **visual ID check**, but face recognition is **called from the CARE server**, not built by us. The system is **trust-based** — no verification the medication was physically taken.
- ~~A robot needs **no GUI** — it consumes API endpoints. The **web UI is for demonstration**.~~
  **CORRECTED (11 Aug):** the **web page is the PO's first priority** and is a real product for humans, not a demo harness. The client is additionally to be designed **phone-based**.
- Must be viewable on both desktop and mobile. — *still correct; the PO accepted a responsive web app in place of native iOS/Android.*

**Data design direction:** fine-grained normalised tables rather than one wide table — e.g. `patient(id, name)` joined to medication/health records on patient ID. Motivated by the PO's wish for the system to be generic. — *still correct, and reinforced: the record must cover prescriptions, exercise, visiting/hospital history, medication history and interaction history.*

**Named technical risk:** concurrent robots. Robot 1 administers medicine A and saves; Robot 2 reads stale state at the same moment, sees medicine A as not given, and administers a second dose. Deferred as a "technical detail" — but see risks below.
**CORRECTED (11 Aug):** dissolved by design — **one local machine cares for exactly one patient**. A reduced version survives: a caregiver editing a prescription on the web page while the client is mid-interaction.
